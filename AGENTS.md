# Guide for Working in This Repository

This file provides guidance to AI agents when working with code in this repository.

`CLAUDE.md`, `AGENTS.md`, and `.github/copilot-instructions.md` are generated by rulesync.
Do not edit them directly. Edit `.rulesync/rules/` and then run `bun run fix`.

## Documentation

This project maintains bilingual documentation:

- **README.md** - English documentation
- **README.ja.md** - Japanese documentation

**Important**: When updating either readme file, the other must be updated accordingly.
Keep both files synchronized with the same content in the appropriate language.

**Important**: README.md's description (line 5) must match action.yml's `description` field.
When updating one, update the other accordingly. Note that action.yml's description should not have a trailing period.

## Security

**Important**: Always consider security and attack resistance when implementing or reviewing changes.
This action runs inside other repositories' workflows.
A weakness here can affect every user of the action.

- Treat all external input as untrusted.
  This includes action inputs, environment variables, and responses from the metrics server.
  Validate them (e.g. with the Zod schema) before use.
- Keep the metrics HTTP server bound to localhost only. Do not expose new endpoints or accept data that changes behavior.
- Never log or write secrets (e.g. `GITHUB_TOKEN`) to the job summary, artifacts, or console output.
- Avoid shell command construction from input. When spawning processes, pass arguments as arrays, never as interpolated strings.
- Pin GitHub Actions to full commit SHAs.
  Keep dependencies minimal, since all dependencies are bundled into `dist/`.
- When reviewing, check `dist/` changes for unexpected code that does not correspond to `src/` changes.
- When fixing a security issue, always write a test that confirms the issue no longer reproduces.
  - Use the input an attacker would send, and check that it is escaped or rejected after the fix.
  - Confirm the test fails against the code before the fix, so it actually detects the issue.

## Architecture

### Build Process

**Critical**: `dist/` directory must be committed. All dependencies are bundled into dist files.

## Implementation Notes

- **Immediate async start**: `Metrics` class starts async collection in constructor without `await`.
  Uses `.catch()` for error handling.
- **Drift-compensated timers**: Uses `Math.max(0, nextUNIXTimeMs - Date.now())` for precise intervals.
- **AbortController timeout**: 10-second timeout for metrics fetch in post execution.
- **Node.js compatibility**: Uses `import.meta.url` with `dirname(fileURLToPath())`.
  Avoids Bun-specific `import.meta.dir`.

## Coding Conventions

- **Zod types**: Use `z.output<typeof schema>` (or `z.input`) for inferred types.
  Do not use `z.TypeOf`, which is deprecated in Zod v4.
- **Comment placement**: Put a comment directly above the line or block it explains.
  When code moves, move its comment with it.
- **No round-trip calculations**: If a value is already known (e.g. an end timestamp), pass it directly.
  Do not derive it again from other fields.
  For example, do not compute `start + duration` after computing `duration = end - start`.
  Keep derived fields such as durations only when consumers need them (e.g. in the artifact).
- **Consistent clamping and validation**: Apply the same clamping or validation to every related value.
  This keeps them consistent (e.g. for clock skew or non-finite timestamps).
  For example, clamp the end time to be no earlier than the start time.
  Then compute the duration from the clamped values.
- **Renderer method roles**: In `src/post/renderer.ts`, `format*` methods build fragments.
  Examples are `formatLegends` and `formatTimes`.
  `render*` methods assemble sections by calling `format*` methods inside template literals.
  Examples are `renderChart` and `renderSection`.
  Keep each method to one of these roles; split a method that does both.

## Pull Requests

- Keep the PR title and description in sync with the actual changes.
  When the implementation changes during review, update the description too.
  This includes changes to the output format and new artifact fields.
